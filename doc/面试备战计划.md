## 高频追问清单（20 题）

> 每题附答案要点，Day 3 任务3 用。

### 架构与模型（5 题）

**Q1：Reactor 模式的核心思想？和 Proactor 区别？**
- Reactor：事件循环等待事件就绪，就绪后通知应用层"你来处理"（同步非阻塞）
- Proactor：事件循环负责完成 IO 操作，完成后通知应用层"已经处理好了"（异步）
- 本项目是 Reactor：epoll 等就绪 → 回调里自己 recv/send

**Q2：epoll 相比 select/poll 的优势？ET/LT 区别？**
- select：fd 集合有上限（1024），每次调用都要拷贝，O(n) 遍历
- poll：去掉了 fd 上限，但仍是 O(n) 遍历
- epoll：内核维护红黑树 + 就绪链表，只返回就绪的 fd，O(1) 等待
- LT（水平触发）：fd 就绪后只要缓冲区还有数据就一直通知
- ET（边沿触发）：只在状态变化时通知一次，必须一次性读完，否则数据残留
- 本项目用 LT（代码里没设 EPOLLET），好处是编程简单不易丢数据

**Q3：为什么主线程只 accept？多线程 IO 的意义？**
- accept 是轻量操作，主线程单独做避免锁竞争
- 工作线程各跑独立 EventLoop，连接分配后互不干扰，无锁
- 多线程利用多核，单线程 EventLoop 会成为 CPU 瓶颈

**Q4：Channel 的职责？一个连接对应几个 Channel？**
- Channel 封装 fd + 关注的事件 + 各类事件回调
- 一个连接对应一个 Channel（Connection 内含一个 Channel）
- 另外 eventfd 也有一个 Channel（EventLoop 里的 _event_channel）

**Q5：事件循环为什么三步？任务池为什么最后执行？**
- 三步：Poll 等就绪 → HandleEvent 处理就绪事件 → RunAllTask 执行跨线程投递的任务
- 任务池放最后：epoll_wait 可能被 eventfd 唤醒，此时任务池已有新任务，先处理就绪事件再执行任务，保证 IO 优先级

### 线程与并发（4 题）

**Q6：RunInLoop / QueueInLoop 区别？**
- RunInLoop：如果当前线程就是 EventLoop 所属线程，直接执行；否则调用 QueueInLoop
- QueueInLoop：压入任务池（加锁），然后写 eventfd 唤醒 epoll_wait
- 关键：所有对 Connection 的操作都通过 RunInLoop 投递到所属线程，保证单线程访问，无需加锁

**Q7：eventfd 的作用？为什么 EFD_NONBLOCK？**
- eventfd 是一个轻量级的进程间/线程间通知机制，本质是一个计数器
- 作用：跨线程投递任务后，唤醒可能阻塞在 epoll_wait 的 EventLoop
- EFD_NONBLOCK：ReadEventfd 时如果无数据（EAGAIN）直接返回，不阻塞；因为 eventfd 只是信号，不需要阻塞读

**Q8：_conns 被多线程访问吗？怎么保证安全？**
- _conns 只由主线程（baseloop）增删
- NewConnection 在 accept 回调中执行（主线程）
- RemoveConnection 通过 _baseloop.RunInLoop 投递到主线程执行
- 所以 _conns 不需要加锁——这是"线程封闭"的设计思想

**Q9：业务回调在哪个线程执行？共享数据怎么办？**
- 业务回调（MessageCallback 等）在连接所属 EventLoop 的工作线程执行
- 多连接可能在不同线程，业务层共享数据需要自己加锁或用线程安全容器
- 项目本身不保证业务数据的线程安全

### 连接与缓冲（6 题）

**Q10：连接状态机四个状态？DISCONNECTING 什么场景？**
- DISCONNECTED：已释放
- CONNECTING：刚创建，还没 Established
- CONNECTED：正常通信
- DISCONNECTING：半关闭，等 out_buffer 发完再释放
- DISCONNECTING 出现在：Shutdown 被调用，或 HandleRead 出错，但还有数据待发送

**Q11：Send 为什么先入缓冲再 EnableWrite？直接 write 行不行？**
- 不行。Send 可能被其他线程调用，直接 write 有竞态
- 拷进 out_buffer 后通过 RunInLoop 投递到所属 EventLoop，由 EventLoop 线程串行发送
- 另外非阻塞 socket 可能写不完（EAGAIN），需要缓冲剩余数据等下次可写

**Q12：写完后为什么 DisableWrite？**
- LT 模式下，如果 out_buffer 已空但仍关注可写事件，epoll 会一直返回可写（因为发送缓冲区始终可写），造成忙等（CPU 100%）
- 所以发完后 DisableWrite，有新数据要发时再 EnableWrite

**Q13：为什么继承 enable_shared_from_this？**
- Connection 由 shared_ptr 管理（_conns 里存的是 shared_ptr）
- 回调函数中需要持有自身的 shared_ptr，防止回调执行期间 Connection 被释放
- shared_from_this() 安全地获取自身的 shared_ptr，而不是裸指针 this

**Q14：半包/粘包怎么处理？**
- TCP 是字节流，没有消息边界
- 本项目的 TCP 层不处理半包/粘包，把数据原样交给应用层（MessageCallback）
- HTTP 层通过 Content-Length 确定正文长度，实现半包处理
- 自定义协议需要应用层自己设计消息边界（如长度前缀）

**Q15：Buffer 怎么扩容？读写偏移如何设计？**
- Buffer 内部是一个可扩容的 char 数组
- 读偏移（readerIndex）和写偏移（writerIndex）
- Write 时如果空间不够，扩容或移动已有数据（compact）
- ReadAbleSize = writerIndex - readerIndex

### 定时器（2 题）

**Q16：时间轮实现原理？复杂度？为什么不用最小堆？**
- 时间轮：一个环形数组，每个槽是一个任务列表，每秒转动一格
- 添加任务 O(1)（计算槽位插入），取消 O(1)，到期执行 O(k)（k 是该槽任务数）
- 最小堆：添加 O(log n)，取最小 O(1)，取消 O(n)（需要查找）
- 时间轮适合大量短周期定时任务（如连接超时），最小堆适合任务数量少但时间跨度大的场景

**Q17：非活跃连接释放的完整链路？**
- EnableInactiveRelease(sec) → TimerAdd(conn_id, sec, Release)
- 每次 HandleEvent（任意事件触发）→ TimerRefresh(conn_id) 延迟超时
- 如果 sec 秒内无任何事件 → 时间轮到期 → 执行 Release → ReleaseInLoop 关闭连接

### HTTP 与改进（3 题）

**Q18：HTTP 解析为什么用状态机？**
- HTTP 请求可能分片到达（一个请求分多个 TCP 包）
- 状态机记录当前解析到哪一步（请求行/头部/正文），新数据到达时从上次状态继续
- 一次性 read 完的假设在 TCP 字节流下不成立

**Q19：和 muduo 的异同？你改进了什么？**
- 相同：Reactor 模型、EventLoop/Channel/Poller 结构、主从线程、定时器
- 简化：muduo 用多 Poller 分发，本项目直接每个 EventLoop 一个 Poller；muduo 的 Buffer 更复杂（readv 分散读）
- 诚实回答：核心架构参考 muduo/视频教程，自己消化后加了 HTTP 示例层和非活跃释放
- 面试技巧：不要说"完全自己写的"，说"基于 muduo 思想实现，重点理解了 X/Y/Z"

**Q20：如果让你优化，改什么？**
- 加压测（qps、连接数、延迟），用数据说话
- 支持 ET 模式提升高并发性能
- 加连接数上限和优雅退出
- HTTP 支持 chunked 传输和 keep-alive
- 加日志分级和性能 profiling

## 面试讲稿模板（Day 3 任务2 用）

### 开场（30 秒）
"我做的这个项目叫 LoopForge，是一个基于 C++11 的轻量级高并发网络库，采用主从 Reactor 多线程模型。主线程负责 accept 新连接，工作线程池各跑一个 EventLoop 处理连接 IO。我实现了 TCP 连接管理、事件循环、线程池、定时器，并落地了 echo 和 HTTP 服务两个示例。"

### 架构（1 分钟）
画架构图讲解：
- 主线程：baseloop + Acceptor，epoll 监听 listenfd
- 工作线程：N 个 EventLoop，每个独立 Poller
- 新连接 round-robin 分配
- eventfd 用于跨线程唤醒

### 六大设计点（2.5 分钟，每个 25 秒）
1. **事件循环三步**：Poll → HandleEvent → RunAllTask
2. **eventfd 跨线程唤醒**：QueueInLoop 写 eventfd，唤醒阻塞的 epoll_wait
3. **线程封闭**：Connection 所有操作投递到所属 EventLoop，无锁
4. **连接状态机**：四状态 + 半关闭，保证数据发完再释放
5. **双缓冲**：in/out buffer，非阻塞 IO 下处理 EAGAIN
6. **时间轮定时器**：O(1) 添加/取消，实现非活跃连接释放

### 验证与反思（1 分钟）
