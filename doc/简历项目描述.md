## 2. 正式版（5 条，推荐）

> 适合：项目是简历主项目、版面充足。每条一行到一行半。

- 基于 `epoll`(LT) + `eventfd` + `timerfd` 实现主从 Reactor 网络库：主线程 Acceptor 只负责 accept，新连接按轮询分配至工作线程的独立 EventLoop，形成**线程封闭**，连接的读写与生命周期管理全链路无需加锁。
- 实现跨线程任务投递：以 eventfd 打断 `epoll_wait` 阻塞来唤醒目标 EventLoop，任务队列用 `mutex + swap` 缩小临界区；对连接的所有操作统一投递回其所属线程执行，保证无锁前提下的时序正确。
- 实现基于**时间轮**的非活跃连接回收，定时任务的添加 / 刷新 / 取消均为 O(1)；配合连接状态机与半关闭语义，保证待发数据全部写出后才释放连接。
- 在库之上实现 **HTTP/1.1 应用层**：状态机式增量解析以应对 TCP 分片到达，正则路由表分发 GET/POST/PUT/DELETE，静态文件服务与 MIME 识别，并以目录深度计数防护 `/../` 路径穿越。
- 对库做健壮性审查并修复两处真实缺陷：修复畸形 `Content-Length` 触发未捕获异常导致**服务进程终止**的进程级 DoS（改为严格解析并施加正文长度上限）；修复 `recv()` 将 EOF 与 EAGAIN 归并、依赖残留 `errno` 判定而造成的**连接泄漏与事件循环空转**，并补注册 `EPOLLRDHUP`。补充单元测试与压测脚本，单机 `___` 并发下 QPS `___`、P99 `___` ms。

## 3. 精简版（3 条）

> 适合：项目是次项目、或简历版面紧张（一页纸塞三个项目时）。

- 基于 `epoll` + `eventfd` 实现主从 Reactor 网络库，通过**线程封闭**使连接读写与生命周期管理全链路无锁，跨线程任务投递以 eventfd 唤醒目标事件循环。
- 基于**时间轮**实现 O(1) 定时任务调度以主动回收非活跃连接；连接状态机以半关闭语义保证待发数据写完后才释放。
- 在其上实现 **HTTP/1.1 应用层**（状态机增量解析 + 正则路由 + 静态文件），并通过健壮性审查修复了畸形 `Content-Length` 致进程终止、EOF 与 EAGAIN 混同致连接泄漏等缺陷。

## 5. 追问预判表

每写一条 bullet，面试官就多一个瞄准点。这张表列出每条最可能招来的追问，以及你**必须能一句话答出来**的内容。

| Bullet | 最可能的追问 | 你必须能答 |
|---|---|---|
| ① 主从 Reactor | 为什么主线程只 accept？ | accept 是轻量系统调用；若主线程还处理读写，accept 会被拖慢，新连接建立延迟上升 |
| ① 主从 Reactor | 为什么每个工作线程独立 EventLoop？ | 共享一个 EventLoop 就要对同一个 epoll 实例和任务队列加锁，锁竞争成瓶颈；独立 = 线程封闭，无锁 |
| ② eventfd | 为什么需要 eventfd？ | 工作线程可能正阻塞在 `epoll_wait`，其他线程要投递任务就得有个 fd 能触发可读事件把它叫醒 |
| ② eventfd | `RunInLoop` 和 `QueueInLoop` 区别？ | 同线程直接执行；跨线程压任务池 + 写 eventfd 唤醒 |
| ② eventfd | 为什么用 `mutex + swap`？ | 加锁只做一次指针交换，把任务处理挪到锁外，临界区从"执行任务"缩到"搬 vector" |
| ③ 时间轮 | 为什么不用最小堆？ | 时间轮添加/取消 O(1)，最小堆取消要 O(n) 查找；连接超时是大量短周期任务，正合时间轮 |
| ③ 时间轮 | 先 tick 前进还是先 clear？ | 必须先 `_tick` 前进再 `clear`，否则槽内任务活不满一个完整周期，延迟少 1 秒 |
| ③ 半关闭 | `DISCONNECTING` 什么用？ | `Shutdown` 后不立即释放，等 `_out_buffer` 写完再 `Release`，否则响应可能发不出去 |
| ④ HTTP 状态机 | 为什么要状态机？ | TCP 是字节流，一个请求可能分多个包到达，状态机记住解析到哪一步，下次从该步续解 |
| ④ 路径穿越 | `/../../../etc/passwd` 怎么防？ | `ValidPath` 按 `/` 切分统计目录深度，出现 `..` 就减一，深度小于 0 直接拒绝 |
| ⑤ 缺陷修复 | `recv()` 返回 0 是什么？ | 对端发了 FIN，优雅关闭。**不是**"暂时无数据"，后者是 EAGAIN |
| ⑤ 缺陷修复 | 这个 bug 是你写的还是原有的？ | **照实说：教程代码就存在**，我是审查时发现的（见下节） |

## 6. 关于「这个 bug 是你自己发现的吗」

面试官**一定会**问到这个。标准答法：

> "这个库是我照着 muduo 的设计思想逐个模块实现的，核心架构不是我原创。但我写完跑通之后，把它当成一份待审查的代码又过了一遍，找到了几个真实缺陷。比如 `Content-Length` 那个——原实现直接调 `std::stol` 且没有异常捕获，客户端发 `Content-Length: abc` 就会抛 `std::invalid_argument`，沿途无人捕获，直接 `std::terminate` 把整个服务进程干掉。一条畸形请求就是一个进程级 DoS。"

**照实说这是教程代码就有的缺陷。** 你的价值在"发现并修复"，不在"写出了有 bug 的代码"——这两件事在面试官眼里完全不同。硬说成自己发现的设计缺陷，反而会被追问细节问穿。

## 7. 压测数字怎么填

跑完 `test/bench.sh`（见配套文档）后，按这个格式写：

```
单机 2 核 4G 虚拟机（VMware），wrk -t2 -c100 压测动态路由，
QPS 约 21000，P99 延迟 5.6 ms，持续 15 秒 RSS 稳定在 3.2 MB
```

**必须带上**：核数、内存、工具与参数。理由有二：

1. 脱开环境的 QPS 没有意义，带上参数才显得你真跑过
2. 面试官问"你怎么测的"时，你的答案是现成的

数字不好看完全没关系——实习面试官看的是"你知道怎么测、知道数据意味着什么"，不是数字本身。**几千 QPS 也照写。**
