## 2. 跑通

示例现在引用的是拆分后的头文件 `include/server.hpp`，Makefile 已带 `-I../../include`。

```bash
cd <仓库>/source/echo && make && ./main      # 监听 8500
cd <仓库>/source/http && make && ./main      # 监听 8085，需在 source/http 下运行（静态目录是 ./wwwroot/）
```

验证：

```bash
# echo
echo hello | nc 127.0.0.1 8500

# http
curl -i http://127.0.0.1:8085/hello
curl -i http://127.0.0.1:8085/index.html
curl -i -X POST -d "username=demo&password=demo" http://127.0.0.1:8085/login
```

**可能踩的坑**：

| 现象 | 原因 |
|---|---|
| `fatal error: server.hpp: No such file` | Makefile 的 `-I../../include` 被改掉了，或不在 `source/xxx` 目录下执行 make |
| `error: 'EPOLLRDHUP' undeclared` | 极少数的老内核/老 glibc；`EPOLLRDHUP` 需要 `/usr/include/sys/epoll.h`，更新 `linux-libc-dev` |
| `assert(IsDirectory(path))` 失败 | http 服务不在 `source/http` 下运行，找不到 `./wwwroot/` |
| 端口被占 | 上次的 `./main` 没退干净，`pkill -x main` |

## 3. 回归验证

```bash
bash test/run_checks.sh
```

脚本做 6 件事，逐项说明它在验证什么：

| 步骤 | 验证内容 | 失败意味着 |
|---|---|---|
| 1 构建 | 两个示例能否编译 | 拆分的头文件有问题，或 Makefile 的 include 路径不对 |
| 2 **单元测试** | `Socket::Recv` 的四种返回值语义 | `recv` 的 EOF/EAGAIN 修复没生效 |
| 3 启动 | 两个服务能否起来 | 端口占用或启动即崩 |
| 4 功能回归 | `GET /hello` 是否 200 | HTTP 层被改坏 |
| 5 **畸形请求** | 4 种非法 `Content-Length` 后进程是否存活、返回码是否符合预期 | 进程级 DoS 未修复 |
| 6 **连接回收 + 空转** | 客户端关闭后是否回收连接、空闲 2 秒 CPU 增量 | 连接泄漏或事件循环空转 |

### 关于第 2 步（最重要）

`recv()` 返回 0 的缺陷**不是必现的**——原实现用 `if (ret <= 0)` 分支，`recv()==0`（EOF）走哪个分支取决于 `errno` 的**残留值**。连接一旦发生过写阻塞（`send` 返回 EAGAIN）或 eventfd 空读，`errno` 就残留 `EAGAIN`，此后对端关闭会被误判成"暂时无数据"，连接永不回收。

所以单元测试先用 `NonBlockRecv` 人为制造一次 EAGAIN 把 `errno` 置位，再让对端半关闭，**确定性地**暴露这个误判：

```bash
cd test && make check
# 期望（修复后）：
#   case 3: [PASS] 对端半关闭返回 -1(EOF)，与 case 1 的 0 区分开
# 期望（修复前）：
#   case 3: [FAIL] ...
```

### 对比"修复前"的表现

```bash
git stash                          # 回到修改前的代码
bash test/run_checks.sh            # 看第 2、5、6 步会怎样
git stash pop                      # 恢复
```

⚠️ 修复前第 5 步的"非数字 Content-Length"会**直接干掉 http 进程**，后续用例全部报"服务进程已不在"，这是预期现象，正是要展示的东西。

## 4. 压测

```bash
bash test/bench.sh
# 或指定参数
DURATION=30 LEVELS="1 10 50 100 200" bash test/bench.sh
```

脚本压两条路径：`/hello`（动态路由，走完整解析 + 正则匹配 + 构造响应）和 `/index.html`（静态文件，走文件读取 + MIME）。

**怎么读结果**：

- **QPS 随并发上升后走平** → 说明 CPU 已打满，服务端到瓶颈了，是正常形态
- **QPS 随并发上升后下跌** → 可能是锁竞争或缓冲区拷贝开销（本项目的 `HandleRead` 每次事件只读一次，高并发下会多绕 `epoll_wait` 几轮）
- **P99 远高于平均** → 长尾。检查是否有个别连接在 `QueueInLoop` 上排队
- **RSS 持续上涨不回落** → 内存泄漏或缓冲区未回收。修复后应当基本平稳
- **非 2xx 响应 > 0** → 服务端在拒请求，查服务端日志

**记录时必须带上**：`nproc`、内存、wrk 参数、压测时长。

## 7. 逐模块吃透路线

每个模块按"设计动机 → 关键机制 → 一个坑点"三段式整理。**验收标准是能不看代码口述**。

### 7.1 EventLoop — 全场最核心

`include/event_loop.hpp`

必须讲清：

- **三步循环**：`Poll()`（事件监控）→ `HandleEvent()`（就绪事件分发）→ `RunAllTask()`（执行任务池）。顺序不能反——IO 就绪事件优先于跨线程投递的任务，否则任务可能饿死 IO。
- **eventfd 唤醒**：线程可能正阻塞在 `epoll_wait`（timeout = -1）。其他线程要投递任务，就写 eventfd（一个被 epoll 监控的 fd），触发可读事件让 `epoll_wait` 立刻返回。`ReadEventfd` 必须处理 EAGAIN（无数据直接返回，不阻塞）。
- **`RunInLoop` vs `QueueInLoop`**：前者同线程直接执行，否则转后者；后者一定入队 + 写 eventfd。
- **`mutex + swap`**：加锁只做一次 `_tasks.swap(functor)`，把任务**处理**挪到锁外，临界区从"执行 N 个任务"缩短到"搬一个 vector"。

坑点：`eventfd` 用 `EFD_NONBLOCK`，读的时候必须容错 EAGAIN，否则会把自己阻塞住。

### 7.2 Poller + Channel

`include/poller.hpp`、`include/channel.hpp`

- **Poller** 只管 `epoll_ctl`（ADD / MOD / DEL）和 `fd → Channel*` 映射，`Poll()` 里 `epoll_wait` 拿到就绪事件后通过 `SetREvents` 回填给 Channel。不关心事件怎么处理——这样换 IO 复用机制只改 Poller，上层不动。
- **`_events` vs `_revents`**：前者是"我想关注什么"（注册给内核），后者是"这次实际发生了什么"（内核返回）。两者不相等是常态（同时关注读写，这次只有读就绪）。
- **`HandleEvent` 的分发顺序**：读事件（`EPOLLIN` / `EPOLLRDHUP` / `EPOLLPRI`）先处理；然后 `EPOLLOUT` / `EPOLLERR` / `EPOLLHUP` 用 `else if` 串起来——因为这三类都可能释放连接，一次只处理一个，避免连接已被释放后还去调另一个回调。

**坑点（本次修复的核心之一）**：`EPOLLRDHUP` 在 epoll 里**必须显式注册**才会返回（只有 `EPOLLERR` / `EPOLLHUP` 是自动上报的）。原代码在 `HandleEvent` 里判断了 `EPOLLRDHUP`，但 `EnableRead()` 只 `|= EPOLLIN`，所以那个分支是**死代码**。修复后 `EnableRead` 注册 `EPOLLIN | EPOLLRDHUP`，`DisableRead` 也同步清掉。

### 7.3 Connection — 状态机 + 双缓冲

`include/connection.hpp`

- **四状态**：`DISCONNECTED` → `CONNECTING`（刚构造，还没 Established）→ `CONNECTED`（可通信）→ `DISCONNECTING`（半关闭，等 `_out_buffer` 发完再释放）
- **双缓冲**：`_in_buffer`（收到但业务还没消费的数据）/ `_out_buffer`（业务要发但还没发出去的数据）
- **`Send` 为什么不直接 `write`**：① `Send` 可能被其他线程调用，直接 write 有竞态；② 非阻塞 socket 一次可能写不完（EAGAIN）。所以先在**调用线程**把数据拷进一个临时 `Buffer`（因为投递是异步的，调用方的 `data` 指针可能已经失效），再 `std::move` 进任务投递到连接所属线程，由该线程串行写出。
- **写完后必须 `DisableWrite`**：LT 模式下 socket 发送缓冲区几乎总是可写，一直注册 `EPOLLOUT` 会让 `epoll_wait` 每次都返回可写事件 → **空转吃满 CPU**。
- **`enable_shared_from_this`**：`Connection` 由 `TcpServer::_conns` 的 `shared_ptr` 管理。回调里要把自身传出去，必须用 `shared_from_this()` 拿到合法的 `shared_ptr`，裸 `this` 构造 shared_ptr 会导致 double free。
- **`Release` 为什么用 `QueueInLoop`**：延迟到本轮事件处理栈完全退出后再销毁对象，避免栈上还有正在使用的 `this`。

**坑点（本次修复的核心）**：`HandleRead` 依赖 `Socket::Recv` 的返回值。原实现把 `recv()` 返回 0（对端 FIN）和 EAGAIN（暂时无数据）**都归成 0**，并且用可能残留的 `errno` 做判断。于是对端优雅关闭时，连接可能既不释放、也不关闭，fd 停在 EOF 可读状态被 LT 模式反复通知 → 空转。修复后返回值明确区分：`>0` 数据 / `0` 无数据 / `-1` EOF / `-2` 出错。

### 7.4 TimerWheel — 时间轮

`include/timer.hpp`

- **结构**：60 个槽的环形数组，每槽一个任务列表；`timerfd` 每秒触发一次可读事件驱动秒针前进。
- **复杂度**：添加 O(1)、刷新 O(1)、取消 O(1)、到期执行 O(k)。
- **`RunTimerTask` 的顺序**：先 `_tick = (_tick + 1) % _capacity`（秒针前进）**再** `_wheel[_tick].clear()`。顺序反了会让槽内任务活不满一个完整周期，延迟少 1 秒。
- **到期为什么靠析构**：`~TimerTask()` 里执行 `_task_cb()`。`clear()` 槽会释放该槽持有的 `shared_ptr`，当某个 TimerTask 的引用计数归零时析构触发 → 任务执行。取消（`TimerCancel`）只是置 `_canceled = true`，析构时就不执行回调。
- **刷新的实现（能答出来很加分）**：`TimerRefresh` 从 `_timers` 取出 `weak_ptr`，`lock()` 成 `shared_ptr` 后**再 push 进新的槽**。同一个 TimerTask 被多个槽共同持有，只有当**所有**槽都被 clear、计数归零时才析构。所以每次刷新都把"最后截止时刻"往后推——这就是延迟超时的机制。
- **`_timers` 为什么存 `weak_ptr`**：若存 `shared_ptr`，任务会被 map 永久持有、永不析构 → 定时任务永远不触发（因为触发逻辑在析构里）。这是很反直觉但必须理解的点。
- **非活跃连接回收的完整链路**：`EnableInactiveRelease(sec)` → `TimerAdd(conn_id, sec, Release)`；每次 `HandleEvent`（任意事件）→ `TimerRefresh(conn_id)` 推迟超时；若 sec 秒内无任何事件 → 时间轮到期 → 析构 → `Release()` → `ReleaseInLoop` 关闭连接。

**坑点**：`_capacity` 固定 60，槽位算的是 `(_tick + delay) % 60`。**`delay > 60` 的任务会落到错误槽位、提前触发**（比如 delay=120 会落到当前槽，约 60 秒后就执行）。HTTP 示例用默认 10 所以没暴露。

### 7.5 TcpServer + Acceptor + ThreadPool

- **Acceptor**：持有 listenfd 和一个 Channel，只做 `accept` + 回调。监听套接字的读事件监控**必须在设置回调之后**才启动（否则可能启动监控后立即有事件，而回调还没设上 → 新连接得不到处理、资源泄漏）。
- **TcpServer::NewConnection**：`_next_id++` → `new Connection(_pool.NextLoop(), ...)` → 设置四个业务回调 + 内部关闭回调 → `Established()` → 插入 `_conns`。
- **`_conns` 不需要加锁**（线程封闭）：只由主线程增删。新增发生在 accept 回调（主线程）；删除通过 `_baseloop.RunInLoop` 投递回主线程执行。
- **`LoopThread` 的同步技巧**：`EventLoop` 对象在线程入口函数的**栈**上构造（`ThreadEntry` 里 `EventLoop loop;`），构造完用 `mutex + condition_variable` 通知 `GetLoop()` 的等待方。这样保证"线程创建了但 EventLoop 还没构造好"时不会拿到空指针。因为 `loop.Start()` 是死循环，指针在进程存活期内一直有效。
- **`LoopThreadPool::NextLoop`**：`_next_idx = (_next_idx + 1) % _thread_count`，轮询分配。注意 `_next_idx` 初值 0，所以**第一个连接分到 `_loops[1]`**，第二个才轮到 `_loops[0]`。
- `SetThreadCount(0)` 表示不创建工作线程，所有连接直接用主 EventLoop。

### 7.6 Buffer + Socket + Any

- **Buffer**：`_reader_idx` / `_writer_idx` 两个偏移。`ReadAbleSize() = writer - reader`。空间不够时先尝试**把可读数据搬到起始位置**（compaction），实在不够才扩容。`GetLine()` 用 `memchr` 找 `\n` 实现按行读取（HTTP 头解析靠它）。
- **Socket**：`Recv` 的四态返回值（见 7.3 坑点）；`Send` 遇 EAGAIN/EINTR 返回 0（表示"没发出去"），真错误返回 -1。
- **Any**：类型擦除容器，用 `holder`/`placeholder<T>` 实现「存任意类型 + 类型安全取回 + 支持拷贝（`clone`）」。`Connection::_context` 用它存协议上下文，使网络库不关心上层是什么协议。
- **`Any::get<T>()` 的脆弱点**：靠 `assert(typeid(T) == _content->type())` 保证类型正确，一旦编译时加 `-DNDEBUG`，assert 消失，类型不匹配就变成静默 UB。而且默认构造的 `Any` 里 `_content == NULL`，此时 `get<T>()` 直接空指针解引用。

### 7.7 HTTP 应用层

`source/http/http.hpp`（约 860 行，全项目最有区分度的一块）

- **`HttpContext` 解析状态机**：`RECV_HTTP_LINE` → `RECV_HTTP_HEAD` → `RECV_HTTP_BODY` → `RECV_HTTP_OVER`。`RecvHttpRequest` 用 `switch` **故意不加 `break`**，让一次调用能连续推进多个阶段（处理完请求行立刻处理头部），只有数据不够时才退出等新数据。
  - 为什么必须用状态机：TCP 是字节流，一个请求可能分多个包到达。状态机记住"解析到哪一步"，下次数据到达从该步续解。假设"一次 read 拿完整请求"在字节流下不成立。
- **行长度保护**：`RecvHttpLine` / `RecvHttpHead` 里若缓冲区数据超过 `MAX_LINE`(8192) 仍未凑出一行，返回 414（URI Too Long）。
- **正文长度**：由 `Content-Length` 决定，按"已收多少 / 还差多少"分块累加（`real_len = content_length - _body.size()`），所以正文分片到达也能正确拼接。
- **路由**：`vector<pair<regex, Handler>>`，按方法分四张表（GET/POST/PUT/DELETE），用 `std::regex_match` 全匹配路径。`/user/(\d+)` 这类正则可用，匹配结果在 `req._matches` 里。
- **静态文件**：`IsFileHandler` 判断四件事（设了根目录 / 方法是 GET 或 HEAD / 路径合法 / 文件存在且是普通文件），路径以 `/` 结尾自动补 `index.html`。`ExtMime` 按后缀查 MIME 表。
- **路径穿越防护**：`Util::ValidPath` 按 `/` 切分路径统计目录深度，遇到 `..` 就减一，深度一旦小于 0 直接拒绝——挡住 `/../etc/passwd` 这类请求。
- **URL 解码**：`UrlDecode(url, convert_plus_to_space)`。**路径**传 `false`（`+` 是字面量），**查询参数**传 `true`（`+` 表示空格，form-urlencoded 语义）。
- **长短连接**：`HttpResponse::Close()` 判断响应头里 `Connection: keep-alive`，`WriteReponse` 据此设置 `Connection` 头，`OnMessage` 依此决定 Shutdown 还是继续处理下一个请求（`while (ReadAbleSize() > 0)` 循环支持一个连接上连续多个请求）。

## 8. 高危追问题库

先脱稿口述，卡壳的再回代码找答案。**每题控制在 30 秒内讲完。**

### 机制类

**Q1. Reactor 和 Proactor 的区别？**
Reactor 等事件就绪后通知应用层"你来读/写"（同步非阻塞）；Proactor 由框架完成 IO 后通知"已经读好了"（异步）。本项目是 Reactor：`epoll` 报就绪 → 回调里自己 `recv`/`send`。

**Q2. epoll 相比 select/poll 的优势？LT 和 ET 区别？**
select 有 1024 fd 上限且每次调用都要拷贝 fd 集合；poll 去掉了上限但仍是 O(n) 遍历；epoll 由内核维护红黑树 + 就绪链表，只返回就绪的 fd。LT 是"只要缓冲区里还有数据就一直通知"，ET 是"只在状态变化时通知一次，必须一次读完"。本项目用 LT（代码里没设 `EPOLLET`），编程简单且不易丢数据。

**Q3. 为什么主线程只 accept？**
accept 本身是轻量的系统调用。如果主线程还兼做读写，accept 会被长耗时的读写拖慢，新连接建立延迟上升。独立出来保证新连接能被及时建立。

**Q4. 一个连接对应几个 Channel？**
一个 `Connection` 内含一个 `Channel`（管 sockfd）。此外每个 `EventLoop` 还有一个 eventfd 的 `Channel`，每个 `TimerWheel` 有一个 timerfd 的 `Channel`。

**Q5. 事件循环为什么任务池放最后执行？**
`epoll_wait` 可能被 eventfd 唤醒（有跨线程任务投递），此时就绪事件和任务同时存在。先处理 IO 就绪事件再执行任务，保证 IO 优先级，避免任务饿死 IO。

### 并发类

**Q6. `_conns` 被多线程访问吗？**
不被。只由主线程增删：新增在 accept 回调（主线程），删除通过 `RunInLoop` 投递回主线程。这是**线程封闭**——不用加锁的正确性来源。

**Q7. 业务回调在哪个线程执行？共享数据怎么办？**
在连接所属 EventLoop 的工作线程。不同连接可能在不同线程，业务层若共享数据需要自己加锁——库本身不保证业务数据的线程安全。

**Q8. 跨线程 `Send` 的完整时序？**
调用线程先把数据拷进临时 Buffer（防指针失效）→ `RunInLoop` 发现非同线程 → `QueueInLoop` 加锁 push 任务池 → 写 eventfd 唤醒目标 EventLoop 的 `epoll_wait` → 目标线程 `RunAllTask` 执行 `SendInLoop` → 数据进 `_out_buffer` 并 `EnableWrite` → EPOLLOUT 就绪 → `HandleWrite` 调 `send` 写出。

### 连接类

**Q9. `recv()` 返回 0 / -1(EAGAIN) / -1(其他) 分别什么含义？**
0 = 对端发了 FIN，优雅关闭；EAGAIN = 非阻塞下暂时无数据；其他负值 = 真错误。**EOF 必须与 EAGAIN 区分**，因为前者要关闭连接、后者什么都不做。这正是本次修复的点。

**Q10. 半包/粘包怎么处理？**
TCP 层不处理，原样交给业务回调，消息边界由应用层定义。HTTP 层靠 `Content-Length` 定长 + 状态机续解还原边界。自定义协议需要应用层自己设计长度前缀之类的边界。

**Q11. 为什么写完后 `DisableWrite`？**
LT 模式下发送缓冲区几乎总是可写，不关会一直返回 EPOLLOUT 造成忙等（CPU 打满）。

**Q12. 连接状态机四个状态？`DISCONNECTING` 什么场景？**
`DISCONNECTED`（已释放）/ `CONNECTING`（刚构造未就绪）/ `CONNECTED`（可通信）/ `DISCONNECTING`（半关闭）。`DISCONNECTING` 出现在 `Shutdown()` 被调用、或读出错但 `_out_buffer` 还有数据待发时——等数据发完再 `Release`，避免响应发不出去。

**Q13. `ReleaseInLoop` 里为什么先 `Remove` 再 `Close`？**
`Poller::_channels` 以 fd 为 key。如果先 `close(fd)` 再移除监控，fd 可能被新连接复用，导致误删/误改新连接的监控项。所以顺序必须是先 `_channel.Remove()` 再 `_socket.Close()`。

### 定时器类

**Q14. 时间轮为什么不用最小堆？**
时间轮添加/取消都是 O(1)，最小堆取消需要 O(n) 查找。连接超时是"大量短周期任务、频繁刷新、偶尔取消"的场景，正是时间轮的强项。最小堆适合任务少但时间跨度大的场景。

**Q15. `_timers` 为什么存 `weak_ptr`？刷新怎么实现延迟？**
见 7.4。核心是：`weak_ptr` 不增加引用计数，任务才能正常析构触发；刷新靠"往新槽再 push 一个 shared_ptr"，靠引用计数把析构推迟到最后一个槽被 clear。

**Q16. 一个连接 10 秒无数据是怎么被自动关掉的？**
`EnableInactiveRelease(10)` → `TimerAdd(conn_id, 10, Release)`。之后每次有任意事件都 `TimerRefresh(conn_id)` 把截止时刻往后推。连续 10 秒无事件 → 时间轮转到该槽 → clear → 引用计数归零 → `~TimerTask` 执行 `_task_cb` → `Release()` → `ReleaseInLoop`。

### HTTP 与安全类

**Q17. 为什么要手写 `Content-Length` 解析，不用 `std::stol`？**
`std::stol` 在输入非法时抛 `std::invalid_argument`，在超范围时抛 `std::out_of_range`。HTTP 头是**不可信输入**，没有 try/catch 就是"一条畸形请求终止整个进程"。手写解析顺带解决了负数转 `size_t` 变成 `SIZE_MAX`（导致连接挂死并无限累积数据）的问题。

**Q18. 路径穿越怎么防的？**
`ValidPath` 按 `/` 切分统计目录深度，`..` 使深度减一，小于 0 即拒绝。这样 `/../` 无法逃出静态资源根目录。

**Q19. HTTP 解析为什么用状态机？**
见 7.7。请求可能分片到达，状态机记住当前阶段以便续解。

**Q20. 和 muduo 的差别？你改进了什么？**
相同：Reactor 模型、EventLoop/Channel/Poller 结构、主从线程、时间轮定时器。简化：muduo 有多个 Poller 做分发，本项目每个 EventLoop 一个 Poller；muduo 的 Buffer 用了 `readv` 分散读，本项目是单块可扩容数组。**照实回答核心架构参考自 muduo**，不要声称自研。

### 实验 1：线程模型

```cpp
// source/http/main.cc
server.SetThreadCount(0);   // 改成 0 / 2 / 5 分别跑
```

观察日志前缀 `[%p ...]`（就是 `pthread_self()`）：

- `0` → 所有连接回调都打印主线程 ID
- `>0` → 不同连接的日志分属不同工作线程 ID

**结论要能说出**：每个工作线程各跑一个 `EventLoop`，连接分配后永久归该线程，因此无需加锁。

### 实验 2：非活跃连接回收

### 实验 4：eventfd 唤醒

### 实验 7：缓冲区上限

### 实验 8（进阶，能出真数据）：单次读 vs 循环读到 EAGAIN

当前 `HandleRead` **每次事件只调一次 `recv`**（最多 65535 字节）。LT 模式下可以改成循环读到 EAGAIN：

```cpp
// include/connection.hpp HandleRead 内，示意
// 注意：每轮都要重算可用空间，否则缓冲区满了还会继续读
char buf[65536];
while (true) {
    uint64_t space = static_cast<uint64_t>(BUFFER_MAX_SIZE) - _in_buffer.ReadAbleSize();
    if (space == 0) return ShutdownInLoop();   // 缓冲区已满，按异常连接处理
    uint64_t read_len = space < (sizeof(buf) - 1) ? space : (sizeof(buf) - 1);
    ssize_t ret = _socket.NonBlockRecv(buf, read_len);
    if (ret == 0) break;                       // EAGAIN：本次读空，退出循环
    if (ret < 0) return ShutdownInLoop();      // -1 EOF / -2 出错
    _in_buffer.WriteAndPush(buf, ret);
    if (_in_buffer.ReadAbleSize() > 0 && _message_callback) {
        _message_callback(shared_from_this(), &_in_buffer);
    }
}
_in_buffer.Shrink();
```

**在压测里对比改动前后的 QPS。** 这是**唯一一个能产生真实"优化前后 QPS 提升"数字的改动**，可以放心写进简历。

⚠️ 但要讲清代价：循环读到 EAGAIN 会让一个高流量连接独占所属线程，其他连接被饿到（长尾延迟变差）。这是 LT + 单线程 EventLoop 的经典取舍，面试时能主动说出这一点非常加分。
